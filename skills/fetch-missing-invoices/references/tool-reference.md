# Tool reference — full contracts

This is the field-by-field contract for every `well_*` tool the fetch-missing-invoices
flow touches. The main file states which tool each step calls and when; this file is
where you check an exact field name, an exact return shape, or an edge case in what a
tool reports. It is not a second source of truth for the click chain rules or the step
order — those stay in `SKILL.md`.

## The flow's tools, each owned by the step that calls it

- `well_list_workspaces` — the workspace read. Returns `workspaces[]` (`workspace_id`, `workspace_name`, `is_primary`, `identity` with `country`, `base_currency`, `fiscal_year_start_month`) plus `session: { pinned_workspace_id, workspace_queue, selected_periods, selected_counterparties }` — the server-held context the cards' clicks write. Renders the workspace picker card (multi-select tiles).
- `well_switch_workspace` — the session write. Accepts `workspace_id`, `workspace_ids` (first = pin, rest = queue), `periods` (`[{ calendar_year, calendar_month }]`), `counterparties` (`[{ company_id, matched_connector_service_id }]`, at most 200), and `ack` (`"connectors"` | `"bank"`). The widget cards call it on their **Use** / **Validate** / **Continue** clicks — and each click also prefills its message in the user's composer; the flow calls the tool itself only for typed answers, matched hints, the text-only vendor pick of step 5, and the multi-workspace re-pin between passes. A `counterparties` call scopes the pick to the workspace it is dispatched to and leaves the pin alone; a switch to another workspace clears the pick.
- `well_wait_for_selection({ kind, timeout_s? })` — the click read, legal only AFTER this conversation has rendered the matching card: its one job is reading the click the user made on that card when their next message is not its prefill. Never at step start, never before the card exists, never as a probe for a pin, selection, pick, or ack — a trusted value lives only in this conversation's history; a fresh conversation trusts none (rule 8), so an unresolved step renders its card at once, no call before the render. `kind` is `"workspace"`, `"periods"`, `"counterparties"`, `"connect_ack"`, or `"bank_ack"`. An already-made selection returns instantly as `{ status: "selected", selection, already_set: true }` — workspace: `{ workspace_id, workspace_queue }`; periods: `{ periods }`; counterparties: `{ workspace_id, counterparties }`; acks: `{ acknowledged: true }`; when nothing is set yet it waits briefly (default 10 seconds) and returns `{ status: "no_selection_yet" }`, a normal result, not an error.
- `well_list_connectors` — the ONLY tool the two connection steps call. `kind: "bank"` at step 3, `from_selection: true` at step 6. Every result reports `scope` — one of the three domains, or `"picked_vendors"` — naming what the list IS, and the card words its title from that field. The scopes are mutually exclusive: `from_selection` cannot travel with `kind` or `q`.
- `well_list_periods` — the period picker read, when present. Each period row carries `bank_transaction_count`, the number of BANK transactions the month holds, and that field is the only signal step 3 accepts. The row's `transaction_count` is a different figure: it counts every transaction the month holds, whatever produced it, so an accounting connector on its own can put thousands of rows behind it and a transaction with no source connector counts there too. A current server emits `0` for a month with no bank coverage rather than omitting `bank_transaction_count`, so an absent count means an older server, or a path that read no period row.
- `well_list_missing_invoices` and `well_preview_invoice_fetch`, when present — both called with `workspace_id` only, **no periods argument**: the server uses the clicked selection, and an error comes back only when no selection exists yet — and never in the same turn as each other. The gap-list rows carry a bounded `transactions` list plus `transactions_omitted`. Both results answer for every month the selection held: each gap-list row, and each counterparty inside the preview's routes, carries its own `calendar_year`, `calendar_month` and `period_label`; `periods_requested` says how many months were read, `periods_covered` names them oldest first, and `months` carries each month's own totals. **The envelope's `calendar_year`, `calendar_month`, `fiscal_year`, `fiscal_period` and `period_label` are present only when the selection held exactly one month** — with several months there is no single label to quote. The preview's agents carry `provider_id` (the identifier the collect link names and a run routes on) plus `domain` and `url` (the portal's host and address, display only), the envelope carries `collect_url` — the collect link for those portals — and it carries `scoped_to_selected_counterparties: true` when the server held a pick for this workspace, which is what tells a preview scoped to the pick from one covering the whole period.
- `well_list_counterparties` — the categorization read, and the ONLY tool that reports how many counterparties carry no industry category. Called with `{ workspace_id, periods }` for the selected months, **its `periods` scope holds only the counterparties whose invoices those months are still missing** — never the months' own counterparties, and never the workspace's. It returns one row per such counterparty per month with `is_categorized` and the row's `categories`, plus `row_count`, `total_count` (DISTINCT counterparties across the window), `categorized_count` and `uncategorized_count` over those rows. Its other scope, `uncategorized_only: true`, sweeps the whole workspace and returns no period figures. **The company-category catalog is not in what you receive.** It rides in the result's `_meta`, which reaches the host and the card and never the model — the card's picker is fed from there. The read that reaches you is `well_query_records` on the `categories` root, which the ban below carves out for step 4's proposal mode alone.
- `well_update_company` — the one write, user-confirmed only, one call per company. Its categories input is **`category_ids`**: the complete set of catalog `category_id` values the company should carry, a replace-set (send the existing ids plus the new one to add, `[]` to clear, omit to leave untouched). `data.relationships.categories` is the REST endpoint's shape, not this tool's; the tool's input schema is strict, so a `relationships` input is refused.
- Well's OAuth / DCR flow when no Well connection exists yet — the moment it returns, retry the failed call in the same turn.

## The full ban, with its one carve-out

Never call `well_get_entity` or `well_get_schema`. Never call `well_query_records` either — no activity checks, no enrichment, no side reads: the flow calls no tool outside a step's own list, every extra widget-bearing call renders an unwanted card, and the missing-invoice read IS the activity check. **`well_query_records` has exactly ONE carve-out**, the same one `categorize-counterparties` takes: in step 4's proposal mode, after the user has explicitly asked for proposals, read the catalog once with `root: "categories"` and `whereClause: { category_type: { _eq: "company" } }`. Without it there are no `category_id` values to write, so the proposal mode could propose but never apply. That read renders a card of the labels, which is why it is legal only in the proposal turn — a turn that renders no other card — and nowhere else. Never call `well_invoke_connector_tool`, any `well_create_*` / `well_delete_*`, any `well_update_*` other than `well_update_company`'s `category_ids`, or any close, lock, or posting tool. This flow reads, and writes only the session context (pin, queue, periods, picked counterparties, acks) and the counterparty categories the user confirmed.
